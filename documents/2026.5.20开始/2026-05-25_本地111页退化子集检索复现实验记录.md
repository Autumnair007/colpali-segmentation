# 2026-05-25 本地 111 页退化子集检索复现实验记录

> 记录目的：把本次本地数据集接入、代码路径、运行方式、结果文件位置、以及对结果的解释统一整理清楚，避免后续把 baseline、multiview 改进、本地适配代码三者混在一起。

## 1. 本次实验的定位

这次实验不是在跑完整的 14 文档 HR benchmark，也不是训练新模型。

本次实验的目标是：

1. 基于已经解压到 `data/degraded_dataset/` 下的本地数据集，接通 ColQwen2 检索流程。
2. 只使用与退化数据严格对应的 111 页主文档子集。
3. 先得到 clean / degraded 的单视图 baseline。
4. 再在同一子集上接入何青泽已经完成的免训练 multiview score fusion 改进。
5. 把所有代码入口、命令、日志、结果文件路径和分析结论记录清楚。

因此，这次结果最适合支撑的结论是：

```text
在本地 111 页 clean/degraded 对齐子集上，
可以稳定复现 ColQwen2 检索流程，
并进一步评估单视图 baseline 与免训练 multiview 改进的表现差异。
```

## 3. 本次使用的数据路径

核心数据路径如下：

```text
data/degraded_dataset/corpus/test-00000-of-00001.parquet
data/degraded_dataset/queries/test-00000-of-00001.parquet
data/degraded_dataset/qrels/test-00000-of-00001.parquet
data/degraded_dataset/images/employment_and_social_developments_in_europe_2024-KEBD24002ENN/
data/degraded_dataset/degraded_image/
data/degraded_dataset/degraded_data/
```

本次 clean / degraded 对齐规则如下：

1. `clean` 使用 `images/employment_and_social_developments_in_europe_2024-KEBD24002ENN/page_001~111.png`
2. `degraded` 使用 `degraded_image/page_xxx/page_xxx_PD_MB_GN_JC_LR_CS.png`
3. `query` 和 `qrels` 从 parquet 中筛选
4. 默认只保留单文档自洽的 174 条 query，不保留 54 条 cross-doc query

这样做的原因是：如果直接把 228 条 query 全保留，会有一部分 query 同时把别的文档页也当作 relevant，结果会影响本地 111 页子集评测的解释性。

## 4. 代码路径与职责划分

这次需要区分三类代码。

### 4.1 何青泽原有改进代码

何青泽本轮已经完成的免训练改进，核心在：

```text
experiments/multiview.py
```

对应提交：

```text
dc7e6d1 添加多视图分数融合实用工具及相应的测试
```

它的作用不是训练模型，而是：

```text
training-free multi-view score fusion
```

当前支持的四个 view：

```text
identity
nlmeans
gaussian
wiener
```

默认 weighted fusion 权重：

```text
identity: 0.70
nlmeans: 0.10
gaussian: 0.10
wiener: 0.10
```

### 4.2 本次新增的本地数据适配入口

为了尽量少动原 benchmark 主流程，这次新增了一个本地入口：

```text
experiments/run_local_hr_benchmark.py
```

它的职责是：

1. 读取本地 `corpus / queries / qrels`
2. 固定选择 111 页 focus 文档
3. 构造 clean 页面路径或指定退化 variant 的页面路径
4. 复用 ColQwen2 和已有指标实现完成检索评测
5. 在本地数据上支持 `singleview` 和 `multiview`

这个文件不是何青泽方法本身，而是为了让现有方法能直接吃本地 111 页子集。

### 4.3 被复用的原项目代码

本次直接复用的关键模块包括：

```text
robust/evaluation/metrics.py
tests/test_multiview.py
colpali_engine.models.ColQwen2
colpali_engine.models.ColQwen2Processor
```

其中：

1. `robust/evaluation/metrics.py` 提供 `nDCG@5 / Recall@5 / MRR`
2. `tests/test_multiview.py` 验证 `multiview.py` 的融合逻辑
3. `ColQwen2` 与 `ColQwen2Processor` 负责 query/page 编码和 `score_multi_vector`

## 5. 实验流程说明

本次实际运行的流程分成四类：

1. `singleview clean`
2. `singleview degraded`
3. `multiview clean`
4. `multiview degraded`

其中每种流程都共享同一套 query 筛选逻辑和同一份 111 页页面集合。

### 5.1 singleview baseline

单视图 baseline 的流程是：

```text
query -> processor.process_queries -> ColQwen2 -> query embeddings
page  -> processor.process_images  -> ColQwen2 -> page embeddings
query/page embeddings -> score_multi_vector -> scores_matrix
scores_matrix -> nDCG@5 / Recall@5 / MRR
```

这里的 `page`：

1. `clean` 时直接使用 clean 页图
2. `degraded` 时直接使用指定退化版本页图

### 5.2 multiview 改进

多视图改进的流程是：

```text
query -> 编码一次
page  -> 分别生成 identity / nlmeans / gaussian / wiener 四个 view
每个 view 单独编码并计算一份 scores_matrix
最后对多份 scores_matrix 做 weighted fusion
```

也就是说，这次 multiview 的改进发生在：

```text
测试时图像视图变换 + 分数级融合
```

而不是：

```text
训练新模型 / 修改模型权重
```

### 9.3 运行时现象

这次 multiview 运行过程中，有几个现象值得记录：

1. `nlmeans` 是最慢的分支，明显比 `identity` 和 `gaussian` 更耗时。
2. `degraded` 上的 `wiener` 也比较慢。
3. `wiener` 分支出现过一次 `scipy.signal` 的 `divide by zero encountered in divide` warning。
4. 该 warning 没有导致进程失败，最终结果仍正常生成。
5. 说明这版 multiview 能跑通，但在课程作业场景下，运行成本要明显高于 singleview。

## 11. 最终分析

### 11.1 退化是否真的会拉低检索效果

会，而且证据很清楚。

单视图下，从 clean 到 degraded 的变化是：

| 指标 | `singleview degraded - singleview clean` |
| --- | --- |
| `nDCG@5` | `-0.10839569363460483` |
| `Recall@5` | `-0.15750547345374938` |
| `MRR` | `-0.03409557110652561` |

这说明当前这份本地 111 页子集，已经足够证明：

```text
退化会显著伤害 ColQwen2 检索表现。
```

### 11.2 你的 multiview 改进在 clean 上是否稳定

是稳定的。

相对于 `singleview clean`，`multiview clean` 三个指标都是轻微正向变化，没有出现“为了鲁棒性反而破坏 clean baseline”的情况。

这与何青泽原文档中的方法定位一致：

```text
先验证免训练 multiview 不会破坏 clean 检索流程。
```

### 11.3 你的 multiview 改进在 degraded 上是否有效

结论是：

```text
有效，但提升幅度偏小，而且不是全指标一致提升。
```

更具体地说：

1. `nDCG@5` 提升了 `+0.005844...`
2. `MRR` 提升了 `+0.015020...`
3. `Recall@5` 下降了 `-0.000916...`

因此在课程作业报告里，建议使用比较克制、准确的表述：

```text
weighted multiview score fusion
在本地退化子集上对排序质量有轻微改善，
尤其体现在 nDCG@5 和 MRR 上；
但对 Recall@5 的改善不明显，甚至略有波动。
```

### 11.4 这组结果意味着什么

它意味着你现在已经有一条完整、可解释、可复现的实验链：

```text
singleview clean
-> singleview degraded 明显下降
-> multiview clean 保持稳定
-> multiview degraded 在部分核心指标上回升
```

对于课程作业来说，这条证据链已经是成立的。

但如果后面想把结论写得更强，还可以继续做：

1. 分别跑单退化类型 `PD / MB / GN / JC / LR / CS`
2. 比较不同 fusion 策略 `max / mean / weighted`
3. 进一步分析为什么 `MRR` 上升而 `Recall@5` 没有同步上升

## 12. 最终结论

到本次实验结束，可以明确下来的结论是：

1. 本地数据集接入是成功的。
2. clean 对应数据不需要额外下载，数据包内已经存在。
3. 本次实验对象应明确为与退化数据严格对齐的 111 页子集，而不是完整 14 文档 benchmark。
4. 这次新增的 `experiments/run_local_hr_benchmark.py` 只是本地数据适配入口，不是何青泽的方法本体。
5. 何青泽的方法本体是 `experiments/multiview.py` 中的免训练多视图分数融合。
6. 单视图 baseline 已经证明退化会显著拉低检索效果。
7. multiview 在 clean 上保持稳定，没有破坏原始检索流程。
8. multiview 在 degraded 上对 `nDCG@5` 和 `MRR` 有轻微改善，但 `Recall@5` 没有明显收益。

因此，最适合写进当前课程作业报告的结论是：

```text
我们已经在本地 111 页退化对齐子集上，
成功复现了 ColQwen2 检索流程，
并验证了退化会显著降低检索效果。

在此基础上，
何青泽提出的免训练 multiview score fusion
能够在不破坏 clean baseline 的前提下，
对 degraded 检索的部分核心指标带来小幅回升。
```
