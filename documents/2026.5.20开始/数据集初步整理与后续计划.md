## 4. 和同事口头说明对照后的核实结果

### 4.1 `pdfs`

`pdfs/` 下共有 16 个文件，其中：

- 14 个是真正的 PDF 文档
- 2 个是元数据文件：
  - `metadata.csv`
  - `metadata_european-reports.json`

我实际核到的 PDF 页数如下：

- `employment_and_social_developments_in_europe_2024-KEBD24002ENN.pdf`：111 页
- `employment_and_social_developments_in_europe-KE0125067ENN.pdf`：25 页
- `estimating_labour_market_transitions_and_skills_investment-KE0125066ENN.pdf`：47 页
- 其余 PDF 合计构成整个 14 文档、1110 页的 HR 集合

这里有一个非常重要的差异：

- 同事口述说“我们这个数据集来自 `employment_and_social_developments_in_europe-KE0125067ENN`，共 111 页”
- 但实际文件里：
  - `employment_and_social_developments_in_europe-KE0125067ENN.pdf` 只有 25 页
  - 真正 111 页的是 `employment_and_social_developments_in_europe_2024-KEBD24002ENN.pdf`

这个差异必须后续优先确认。

### 4.2 `images`

同事口述说 `images` 是 111 张 PNG。

实际解压后不是这样。`images/` 下目前有两个文档子目录：

- `employment_and_social_developments_in_europe_2024-KEBD24002ENN`：111 张 PNG
- `estimating_labour_market_transitions_and_skills_investment-KE0125066ENN`：47 张 PNG

合计是 158 张 PNG，而不是 111 张。

不过从脚本来看，退化流程只使用第一份 111 页文档。

### 4.3 `degraded_image`

`degraded_image/` 下共有：

- 111 个页目录：`page_001` 到 `page_111`
- 6993 张退化图片

每一页恰好 63 张退化图，对应 6 种退化的所有非空组合：

- 单退化 6 种
- 2~6 种组合退化共 57 种
- 合计 63 种

从文件名和脚本定义看，6 种退化缩写分别是：

- `PD`：Perspective Distortion，透视畸变
- `MB`：Motion Blur，运动模糊
- `GN`：Gaussian Noise，高斯噪声
- `JC`：JPEG Compression，JPEG 压缩
- `LR`：Low Resolution，低分辨率
- `CS`：Color Shift，颜色偏移

例如：

- `page_098_PD.png`
- `page_098_MB_GN_JC_LR_CS.png`

说明文件名就是“原始页号 + 退化组合”。

### 4.4 `degraded_data`

`degraded_data/` 下有 111 个 JSON：

- `page_001.json`
- `page_002.json`
- ...
- `page_111.json`

每个 JSON 都有 63 个键，和该页的 63 张退化图一一对应。

这些 JSON 记录的不是标签文本，而是退化参数本身。例如：

- `PD` 里有 `src_pts` / `dst_pts`
- `MB` 里有 `kernel_size` / `angle`
- `GN` 里有 `mean` / `sigma`
- `JC` 里有 `quality`
- `LR` 里有 `scale`
- `CS` 里有 `B_shift` / `G_shift` / `R_shift`

组合退化会嵌套保存各个子退化的参数。

这意味着：

- `degraded_image` 是结果图
- `degraded_data` 是生成结果图时用到的参数记录

### 4.5 `corpus`

`corpus/` 下有 3 个文件：

- `test-00000-of-00001.parquet`
- `preview.xlsx`
- `to_excel.py`

其中：

- `to_excel.py` 明确写的是：用 `pandas.read_parquet()` 读取 `parquet`，再导出为 `preview.xlsx`
- `preview.xlsx` 表头我已经直接读出来了，字段是：
  - `corpus_id`
  - `image`
  - `doc_id`
  - `markdown`
  - `page_number_in_doc`

这说明 `corpus` 的核心结构就是“页级样本”：

- `image`：页面图像内容
- `doc_id`：文档 ID
- `markdown`：OCR/文本抽取结果
- `page_number_in_doc`：页号

另外，`preview.xlsx` 里能看到 `image` 这一列不是文件路径，而是直接嵌入/序列化后的图像数据。

### 4.6 `documents_metadata` / `queries` / `qrels`

这说明：

- 要么这份包本来就混合了多个文档的原始图
- 要么有人后续额外补跑过 PDF 转图

### 疑点 3：`corpus` 里的 parquet 还没做正式解析

目前我已确认：

- 文件格式是 `parquet`
- `to_excel.py` 用 `pandas.read_parquet`
- `preview.xlsx` 表头和 README 里的 schema 对得上

但当前环境缺少这些常用依赖：

- `pandas`
- `pyarrow` 或其他 parquet 读取后端
- `openpyxl`
- `PyPDF2`

所以如果后续要系统读取 `corpus/documents_metadata/queries/qrels`，需要补齐读取依赖。

## 9. 我建议的后续工作顺序

下面是我认为最稳妥的推进顺序。

### 第一步：先把“工作对象”确认死

先确认我们后续到底处理哪一层：

- 只处理 111 页退化子集
- 还是处理整个 14 文档 HR benchmark

如果只做当前退化任务，大概率应以：

- `employment_and_social_developments_in_europe_2024-KEBD24002ENN`

作为主对象。

### 第二步：补做一份严格的数据映射表

后续我建议整理出一张明确映射：

- 原始 PDF
- 原始页图
- 退化页图目录
- 退化参数 JSON
- `corpus` 中对应的 `doc_id`
- `page_number_in_doc`

目的：

- 保证我们知道每一页、每一张退化图、每一条文本到底怎么互相对应

### 第三步：正式解析 `corpus`

需要补依赖后，做这几件事：

- 打开 `corpus/test-00000-of-00001.parquet`
- 确认里面到底覆盖哪些 `doc_id`
- 验证 111 页目标文档是否完整在其中
- 确认 `markdown` 字段质量
- 看 `image` 字段是否真的能直接恢复页图

### 第四步：核对退化子集和 `corpus` 的对齐情况

重点核对：

- `degraded_image/page_XXX` 对应的是不是 `corpus` 里同一 `doc_id`、同一页号
- 页号是 1-based 还是 0-based
- 图像尺寸、文本页号、文件名页号是否完全一致

### 第五步：再决定后续代码要做什么

等上面都确认清楚后，再决定具体写什么代码会更稳。大概率会落在下面几类任务之一：

- 写数据加载器
- 写原图/退化图/参数/文本的对齐脚本
- 写样本检查和可视化脚本
- 写训练/评估前的数据准备脚本
