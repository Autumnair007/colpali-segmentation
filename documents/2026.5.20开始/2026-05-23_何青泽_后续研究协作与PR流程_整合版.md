# 何青泽：后续研究、组内协作与 PR 流程（整合版）

> 日期：2026-05-23  
> 版本定位：整合版，用于替代前面分散的“后续研究路线”“组内协作说明”“最小协作指标”等文档中的协作与规划部分。  
> 当前结论：课程作业阶段不需要把流程设计得过重。短期内大家应围绕现有 `experiments/run_benchmark.py`、两个 ViDoRe 子集、`nDCG@5 / Recall@5 / MRR` 三个主指标协作。何青泽当前最适合提交四视图 multiview baseline，后续等退化数据和复原结果到位后再扩展真实退化实验。

## 1. 一句话定位

何青泽当前负责的方向应当是：

```text
退化不变特征策略：
分析退化如何影响 ColQwen2 的表示和检索分数，
并提供特征侧或测试时的缓解方法。
```

当前已完成的四视图多视图融合，应定位为：

```text
冻结 ColQwen2 条件下的免训练 baseline。
```

它适合作为现在的阶段性 PR，不需要继续扩大成一个完整的新评估框架。

## 2. 课程作业场景下的合理目标

这是课程作业，不是正式论文，因此目标应当务实：

1. 每个人有清楚的模块贡献。
2. 代码能通过 GitHub PR 共享。
3. 实验能在本地复现。
4. 结果能用同一批数据集和同一套指标比较。
5. 报告里能讲清楚每个人做了什么。

不建议当前阶段追求：

1. 训练一个完整的新模型。
2. 覆盖很多数据集和很多退化组合。
3. 设计复杂的数据协议。
4. 每个人各自维护一套评估脚本。
5. 把别人的模块也全部包到自己的工作里。

当前最稳的路线是：

```text
先把最小可运行链路跑通，再根据真实退化数据逐步加深。
```

## 3. 基于当前项目的最小协作约定

### 3.1 统一实验入口

短期内大家尽量统一使用：

```text
experiments/run_benchmark.py
```

如果新增方法，优先考虑：

```text
新增 --condition
或在现有 condition 下新增参数
```

不要一开始就写一套完全独立的评估脚本，否则最后结果很难合并。

### 3.2 统一默认数据集

短期统一使用：

```text
vidore/docvqa_test_subsampled
vidore/infovqa_test_subsampled
```

原因：

1. 这两个数据集项目里已经配置。
2. 你之前已经跑过 clean baseline。
3. 数据量相对可控。
4. 方便组内快速对齐结果。

### 3.3 统一主指标

短期统一报告：

```text
nDCG@5
Recall@5
MRR
n_samples
```

这些指标已经在：

```text
robust/evaluation/metrics.py
```

里实现，并被：

```text
experiments/run_benchmark.py
```

调用。

表示一致性指标、embedding 偏移指标可以作为后续加分项，不建议当前就作为所有人的硬性接口。

### 3.4 统一结果保存

当前 `run_benchmark.py` 会保存：

```text
results/results_{tag}.json
results/{timestamp}/results_{tag}.json
```

建议组内比较时优先使用 timestamp 目录下的结果，因为它不会被后续运行覆盖。

### 3.5 统一核心输出概念

当前检索评估的核心是：

```text
scores_matrix: [num_queries, num_docs]
```

不管是你的 multiview，还是郭明坤的 late interaction 加权，最好最后都能输出这个形状的 score matrix，然后统一走：

```text
compute_metrics(scores_matrix)
```

这是当前阶段最重要、最轻量、最实际的接口约定。

## 4. 各成员任务边界

不需要深入分析每个同学的技术细节，只需要知道他们大概交付什么、你需要对接什么。

| 成员方向 | 主要负责内容 | 交付内容 | 你需要关心什么 |
| --- | --- | --- | --- |
| 退化数据构建 | 构造或整理退化文档图 | degraded 图、退化类型、退化强度、样本对应关系 | clean/degraded 是否能对齐 |
| 图像复原/预处理 | 对退化图做复原或增强 | restored 图、复原方法名、参数 | restored 是否能追溯到 degraded |
| 郭明坤 | 退化感知 late interaction 加权机制与整体评估 | 加权打分方法、统一评估结果表 | score matrix、ranking、指标口径 |
| 何青泽 | 退化不变特征策略 | multiview baseline、特征偏移分析、后续校准方法 | 不把退化生成和整体评估全包 |

你当前不应该替别人做完整退化数据生成，也不应该替郭明坤维护整体评估。你的核心是把自己的特征侧方法做清楚。

## 5. 你和郭明坤的合作边界

你和郭明坤的工作最容易交叉，因为都靠近 ColQwen2 的 MaxSim/late interaction 阶段。

### 5.1 郭明坤更偏什么

郭明坤更适合负责：

1. 退化感知 patch/token 权重。
2. late interaction 阶段的加权机制。
3. 统一指标汇总。
4. 整体结果表。

他的关键词可以理解为：

```text
patch confidence
late interaction weighting
overall evaluation
metric aggregation
```

### 5.2 你更偏什么

你更适合负责：

1. 多视图得分融合 baseline。
2. clean/degraded/restored/method 之间的检索表现比较。
3. 后续如果有时间，做 embedding 偏移分析。
4. 再后续可以尝试简单的 embedding 校准。

你的关键词可以理解为：

```text
degradation-invariant feature
multiview fusion
clean-degraded consistency
feature calibration
```

### 5.3 你们现在只需要先对齐什么

不要一开始就对齐很复杂的 token-level embedding 格式。当前只需要先问清楚：

```text
最终评估入口由谁维护？
你的方法最后是否也输出 scores_matrix？
我的 multiview 输出 scores_matrix/ranking 给你是否够用？
condition 命名是否统一？
最终结果表由谁合并？
```

最小协作方式：

```text
你输出 method scores 或 ranking
郭明坤统一汇总不同方法的指标
你根据统一指标写自己方法的分析
```

这样不会变成你一个人把整体评估全包了。

## 6. GitHub PR 协作方式

既然组内准备用 GitHub PR 共享内容，建议流程保持轻量。

### 6.1 你的当前 PR

当前最适合提交的 PR 是：

```text
Add training-free multiview score fusion benchmark
```

包含：

1. `experiments/multiview.py`
2. `experiments/run_benchmark.py` 中的 `--condition multiview`
3. `tests/test_multiview.py`
4. clean 稳定性结果说明
5. 运行命令

暂时不包含：

1. 真实退化数据实验。
2. embedding 分析脚本。
3. 新的整体评估框架。
4. 复杂 metadata 协议。
5. 郭明坤的 late interaction 加权机制。

### 6.2 PR 说明建议

你的 PR 可以这样写：

```text
本 PR 新增一个免训练多视图得分融合 baseline，用于后续退化图到位后的鲁棒性实验。

主要改动：
1. 新增 experiments/multiview.py，实现 identity/nlmeans/gaussian/wiener 四个 view。
2. 在 experiments/run_benchmark.py 中新增 --condition multiview。
3. 支持 max/mean/weighted 三种 score-level fusion。
4. 支持 --local-files-only、--model、--processor、--device、--score-batch-size。
5. 新增 tests/test_multiview.py，覆盖 view 校验、权重归一化和融合逻辑。

实验结果：
identity-only 与 clean baseline 基本一致；
四视图 weighted fusion 在 clean 数据上没有明显性能波动。

限制：
当前 PR 不包含真实退化图实验，不声称已经提升真实退化鲁棒性。
```

### 6.3 本地使用别人 PR

如果别人 PR 已经合并到主仓库：

```bash
git checkout main
git pull
```

如果 PR 还没合并，但你想先试：

```bash
gh pr checkout PR编号
```

或者让对方告诉你分支名：

```bash
git fetch origin 分支名
git checkout 分支名
```

如果你们使用 fork 工作流，通常是：

```bash
git fetch upstream
git checkout main
git pull upstream main
```

实际使用 `origin` 还是 `upstream`，取决于你们仓库设置。

### 6.4 数据不要全放 GitHub

大图像、模型权重、结果缓存不建议直接进 GitHub。更合理的是：

1. GitHub 放代码、配置、运行说明、少量 metadata。
2. 图像数据通过网盘、服务器目录或 Hugging Face Dataset 共享。
3. 本地运行时通过参数指定数据路径和模型路径。

## 7. 是否需要等别人数据做完

不需要完全等。

你现在可以先做：

1. 提交 multiview baseline PR。
2. 和郭明坤对齐 score matrix/ranking 接口。
3. 准备后续 degraded/restored 图到位后的运行命令。
4. 用现有 clean 数据保证你的代码稳定。

需要等别人的部分：

1. 最终 degraded 图。
2. 退化类型和强度说明。
3. restored 图。
4. 最终整体评估表。

所以当前策略是：

```text
不空等，但也不抢别人的模块。
```

你先把自己的 baseline 做成 PR，后续等数据和评估接口到位，再接入真实退化实验。

## 8. 后续真实退化图到位后怎么做

后续至少比较四组：

```text
clean
degraded
restored
your_method
```

它们分别表示：

| 条件 | 作用 |
| --- | --- |
| `clean` | 原始性能上限 |
| `degraded` | 退化造成的性能损失 |
| `restored` | 图像复原能恢复多少 |
| `your_method` | 你的特征侧方法能缓解多少 |

不要只用 restored 图。因为如果只看 restored，就不知道：

1. 原始退化到底造成了多少损失。
2. 复原到底恢复了多少。
3. 你的方法相比 degraded/restored 是否真的有价值。

## 9. 后续如果要加深你的研究

当前 PR 不建议加更多功能，但后续可以按轻重顺序推进。

### 9.1 第一阶段：保留 multiview baseline

真实退化图到位后，先跑：

```text
identity
identity + gaussian
identity + wiener
identity + nlmeans
identity + best_view
```

不建议一上来就只跑完整四视图，因为它开销比较大。

### 9.2 第二阶段：表示一致性分析

如果课程时间允许，可以分析：

```text
clean embedding
degraded embedding
restored embedding
method embedding
```

看它们谁更接近 clean。

但这不是当前 PR 必须内容。

### 9.3 第三阶段：简单 embedding 校准

如果还想更贴近“退化不变特征学习”，可以尝试轻量方法：

```text
页面均值去偏
退化方向消除
简单门控/adapter
```

这些可以作为后续 PR 或报告扩展，不要和当前 multiview baseline 混在同一个提交里。

## 11. 白话流程

整个项目可以简单理解成：

```text
有人把文档图弄坏，得到 degraded 图。
有人尝试把 degraded 图修好，得到 restored 图。
你看 ColQwen2 在这些图上的检索分数怎么变，并尝试用特征侧方法缓解。
郭明坤把不同方法放到统一评估里，汇总结果。
大家把各自贡献写进课程报告。
```

你的当前动作就是：

```text
先把四视图 multiview baseline 提交上去。
它能跑，有测试，有 clean 稳定性结果。
后面等组内数据和评估接口到位，再继续扩展。
```

## 12. 最终建议

当前最推荐：

1. 不再扩大当前 PR。
2. 提交四视图 multiview baseline。
3. PR 里明确说明没有真实退化实验。
4. 和郭明坤先对齐 `scores_matrix` 和评估入口。
5. 等 degraded/restored 数据小样本到位后先联调，再扩大实验。

这样做最符合当前项目状态，也最符合课程作业的工作量。
